# 销售 Agent：从零搭建与后续交付路线图

创建日期：2026-10-29。当前状态：路线设计，尚未开始新项目实现。

## 1. 搭建方式与最终目标

按“独立学习工程，从零逐步实现”的方式推进。老师的 SaleAIbot 用于对照业务和复用经过理解的设计，Claude Code 用于学习记忆、工具、编排和权限。新工程名称和实际位置在第一课确定，本路线不预先创建业务工程或改写老师示例。

最终交付：销售登录后创建客户会话，手动录入或确认截图转录；系统理解意图、读取相关客户记忆、调用授权业务工具、依据审核知识生成并检查建议；销售编辑、复制及补录实际发送结果；同一引擎支持语音、评测和多端。知识和话术按审核、评测、发布、回滚持续改进。

首个业务切片只做三件事：**查课程价格、查退款政策、必要时转人工**。先用明确标记为合成的产品和聊天验证系统；真实业务数据由业务负责人核实后发布。

统一贯穿的示例：

1. 客户：“这个课多少钱？学不会能退吗？”——缺产品，先澄清。
2. 客户明确课程——分别查询本产品价格和退款条款；没有条款则说明待核实。
3. 客户提供目标、基础与时间——记录有来源的事实。
4. 后续追问、超过 16 条、修改目标——验证记忆延续与冲突处理。
5. 知识更新或销售接管——旧建议失效。
6. 销售修改建议、复制、补录实际已发送——检查事实，区分草稿和实际对话。

## 2. 默认技术选择

| 范围 | 初期选择 | 后续升级依据 |
|---|---|---|
| 后端 | Python 3.12、FastAPI、Pydantic | 与示例接近，方便理解和对照 |
| 模型接入 | HTTPX + 兼容模型 API + 可替换 Mock | 先固定协议和失败行为，再比较模型 |
| 持久化 | SQLAlchemy 2、Alembic、SQLite | 正式多用户并发部署按压测迁 PostgreSQL |
| 工作台 | 简单 HTML/CSS/JavaScript | 业务稳定、交互复杂后再决定是否引入前端框架 |
| 知识检索 | 产品/意图过滤 + 关键词检索 | 用召回评测证明需要后，再引入混合/向量检索 |
| Agent 编排 | 显式 Python 服务和类型契约 | 首期直接看清调用链，框架选型不作为前置条件 |
| 测试 | pytest、HTTPX/接口测试、必要前端测试 | 高影响行为、状态一致性和实际业务验收优先 |
| 交付 | 本地开发，随后 Docker/HTTPS/CI | 先验证应用，再建设目标环境部署 |

初期保持单体服务，用模块隔离领域；不一开始拆微服务。测试中替换模型、时间和外部渠道，默认不产生真实模型费用或客户外发。

## 3. 每阶段的共同学习方式

每阶段都执行：**解释概念 → 画清数据流 → 实现最小增量 → 运行观察 → 验证关键场景 → 回顾并记录版本**。

- 先说明本阶段解决什么问题、为什么需要这些对象。
- 分小步修改，解释关键代码与调用关系，让学习者能够复述。
- 提供可直接运行的命令、接口请求和预期结果。
- 对失败情况说明错误在哪里，不用一次性生成整个项目掩盖问题。
- 每阶段有可演示成果和验收清单；达到要求后再进入下一阶段。
- 持续更新阶段状态、已完成内容、遗留问题和业务待确认项。

## 4. 分阶段路线

### 阶段 0：锁定首个业务切片

学习：产品范围、用户故事、业务事实与模型输出的区别。

- [ ] 把 PRD 转成“首版必做 / 后续增加 / 明确不做”。
- [ ] 定义合成课程 ID、价格、合同和知识来源，不当成真实商品。
- [ ] 准备正常询价、缺产品、多意图、退款申请、无知识和保证就业等样例。
- [ ] 明确平台只辅助草拟，实际发送与退款等操作由人工完成。

产出：一页 MVP 范围、合成业务资料、场景验收表。

验收：能讲清第一个版本为谁服务、做什么、何时澄清、何时转人工。

### 阶段 1：创建可运行工程

学习：虚拟环境、依赖、配置、FastAPI 路由与开发启动流程。

- [ ] 确定新项目目录，初始化 Git 和依赖管理。
- [ ] 建立应用入口、配置对象、日志和环境变量示例。
- [ ] 实现进程健康检查，启动 API 和接口文档。
- [ ] 配置秘密不进入版本库、开发/测试数据分离。

产出：可启动服务、README、配置示例。

验收：从新终端按 README 启动，健康接口正常；进程健康不伪装为模型或数据库就绪。

### 阶段 2：会话、消息和数据库

学习：实体、数据库迁移、事务、消息顺序、幂等和乐观锁。

- [ ] 建立组织、用户、客户、会话、消息与建议的基础数据模型。
- [ ] 数据库迁移、会话创建、消息写入和历史读取。
- [ ] 区分客户、人工已发、系统记录和建议草稿。
- [ ] 加消息幂等键、会话版本与版本冲突响应。
- [ ] 在数据模型中预留真实组织归属；本地身份可暂用测试主体，面向用户前接真实认证。

产出：持久化文字会话 API。

验收：重启历史仍在，重复提交不重复入库，两个旧版本请求不能静默覆盖；草稿不算已发送。

### 阶段 3：模型网关与结构化生成

学习：Prompt、上下文、结构化输出、异步请求、超时和依赖注入。

- [ ] 定义可替换的 ModelGateway 和离线 Mock。
- [ ] 实现最小文本请求、严格 JSON 解析与 Pydantic 校验。
- [ ] 返回请求级结果和错误；记录模型、参数、提示版本、耗时及可获得的 token 使用量。
- [ ] 处理未配置、超时、限流、断连、非法 JSON 和截断输出。
- [ ] 获得实际模型配置后用合成内容单独验证真实调用。

产出：稳定模型适配层和离线可演示的回复能力。

验收：模型坏输出不能直接进入业务；失败状态可观察，不假称业务操作成功。

### 阶段 4：审核知识与带来源的检索

学习：RAG 的基本链路、检索范围、知识版本和事实约束。

- [ ] 建模产品、FAQ、条款、来源、审核状态、适用范围和有效期。
- [ ] 实现草稿、审核、发布快照和回滚的最小流程；先用测试审核主体，正式身份在阶段 9 接入。
- [ ] 按组织、产品、意图检索已发布有效知识。
- [ ] 定义无命中、过期和冲突状态；缺产品先询问。
- [ ] 基础事实校验从此阶段开始，避免无来源报价。

产出：回答有来源、无来源会停止猜测的知识问答。

验收：草稿、其他产品及过期条款不作为确定事实；FAQ 问题文本不充当答案依据。

### 阶段 5：受控工具层

学习：工具与普通函数的区别、输入输出 Schema、授权与幂等。

- [ ] 建立工具定义、注册表、授权器和执行器。
- [ ] 先完成 FAQ、产品条款、退款条款、人工转接四类工具。
- [ ] 统一返回状态、数据、来源、版本、耗时和错误码。
- [ ] 执行前校验主体、组织、会话归属、参数和知识可见范围。
- [ ] 写入工具使用稳定幂等键；工具预算与超时受服务器控制。

产出：有授权和审计的业务工具目录。

验收：未注册工具、越权资源、缺参数被拒绝；重复转人工不产生重复任务。认证主体初期可由测试夹具注入，但不能由模型或正文自行声明权限。

### 阶段 6：统一单轮 Agent 编排

学习：Agent 状态、意图判断、工具结果回填和有边界的决策流程。

- [ ] 定义 TurnInput、IntentResult、ToolPlan、ToolResult、GuardResult 和 TurnResult。
- [ ] 建立快速、澄清、复杂、高风险四条路径。
- [ ] 快速路径一次生成；复杂路径先判断意图，服务器映射工具，按需再次生成。
- [ ] 缺信息或需要人工时提前结束；强风险规则优先于 FAQ 分数。
- [ ] 加入每轮调用数量、总时限、取消和重试限制。
- [ ] 保存可审计步骤，不索取或保存模型隐藏思维链。

产出：统一 SalesTurnEngine，后续 Web、重生成、语音、评测共用。

验收：贯穿样例可完整运行；多意图分别查证；模型不能自授工具权限或声称已退款。

### 阶段 7：结构化记忆与上下文管理

学习：历史记录、客户事实、会话摘要、组织知识和过程经验的区别。

- [ ] 保存目标、基础、时间、预算、产品和顾虑等有依据的事实。
- [ ] 事实关联来源消息、确认状态、更新版本和失效条件。
- [ ] 客户修正时保留旧值和审计；矛盾信息先澄清。
- [ ] 组合近期原文、已确认事实、早期摘要和本轮相关知识。
- [ ] 设上下文预算与相关召回，保存本轮实际使用的上下文快照。

产出：能延续长对话、可解释和可纠错的记忆服务。

验收：超过 16 条仍使用已确认需求；不同客户记忆隔离；未发送草稿不会变成客户经历或销售承诺。

### 阶段 8：最终护栏与建议有效性

学习：业务事实校验、状态一致性、并发与版本依赖。

- [ ] 校验价格/产品绑定、合同条款、统计口径、支持政策及承诺表达。
- [ ] 为知识、记忆、控制、策略和消息记录依赖版本。
- [ ] 生成中变化拒绝旧结果提交；生成后变化使旧建议失效。
- [ ] 原始生成、重生成、人工编辑复制、语音共用校验。
- [ ] 返回可操作的降级行为和风险代码。

产出：统一 FinalGuard 和建议失效机制。

验收：无依据编辑价格、跨产品套用、知识回滚、控制权变化等关键场景被正确处理。

### 阶段 9：真实身份、组织和审核权限

学习：认证、授权、角色、资源归属、设备和服务身份。

- [ ] 使用成熟密码散列组件，实现登录、刷新、退出、设备撤销及账号停用。
- [ ] 接入销售、主管、知识编辑、业务审核、系统管理角色。
- [ ] 工具与 API 共用服务器身份和资源授权规则。
- [ ] 审核人从认证主体派生，不能信任请求中的姓名字段。
- [ ] 建立独立限权服务身份、注册/登录与模型调用防滥用策略。

产出：可支撑团队协作的身份权限体系。

验收：跨销售/组织越权失败；撤销立即生效；系统配置权限不能替代业务事实批准。此阶段完成前，开发功能仅用于本地合成数据。

### 阶段 10：销售工作台与人工协作闭环

学习：前后端 API、异步状态、草稿和实际消息的区别。

- [ ] 登录、客户创建/筛选、时间线、建议、来源、风险及下一步展示。
- [ ] 编辑、重生成、复制、放弃及人工已发原文补录。
- [ ] 接管、释放、关闭/重开与操作版本冲突。
- [ ] 原样采用、编辑后采用、未发送与未知结果分别记录。
- [ ] 断网重试保留正确幂等键，不丢正在编辑的草稿。

产出：网页可完成的销售主流程。

验收：新客户可以直接手动开始；复制不标成已发送；新消息到来时旧草稿明确失效。

### 阶段 11：截图采集、转录预览与纠错

学习：多模态输入、文件校验、预览确认和信息来源。

- [ ] 先做网页 PNG/JPEG 上传，再做 Windows 可见窗口截图。
- [ ] 校验文件、像素、大小、标题、会话类型、文字和发言方向。
- [ ] 显示原图与转录，支持正文、角色、时间纠错后确认。
- [ ] 临时图片过期丢弃；正式记录保留来源和修正审计。
- [ ] 检测重复/重叠/乱序，无法确定时要求核对。

产出：受控的首次对话导入。

验收：未确认不入正式会话；PNG/JPEG 在真实客户端协议下均可用；预览过期、取消、重复确认均行为明确。

### 阶段 12：完整评测与审核发布

学习：功能测试、质量评测、开发集/冻结集、发布门槛和反馈学习。

- [ ] 早期场景表扩成完整 Agent 评测，不只检查模型回复函数。
- [ ] 按整段会话划分开发与独立验收数据；脱敏导出、标注和配置快照。
- [ ] 覆盖长记忆、多意图、工具授权、事实、注入、并发、失败和人工操作。
- [ ] 统计正确性、风险漏报、工具成功率、采纳/编辑/放弃、延迟和费用。
- [ ] 从脱敏反馈提议 Skill，经过人工审核、独立评测、发布与回滚。

产出：可重复的质量报告和发布流程。

验收：能用同一数据比较版本；自动规则分数和人工结论区分；知识/Skill 不自动自我发布。测试从早期各阶段持续建设，本阶段负责整合质量体系。

### 阶段 13：语音 API 与 ASR/TTS 编排

学习：服务调用、轮次状态、取消、实际播报与上下文同步。

- [ ] 以最新 PRD 的 POST /voice/turns 统一接口合约。
- [ ] 实现服务身份、session/turn 命名空间、请求哈希、幂等及版本校验。
- [ ] 统一长度/角色/频率限制和错误响应；模型不可用明确返回。
- [ ] 先用模拟 ASR/TTS，再验证真实语音平台协议。
- [ ] 先完成审核文本直入 TTS；按风险决定固定提示、澄清或转人工。
- [ ] 插话取消、迟到丢弃、一轮双答检测，只将实际播报内容记入后续上下文。

产出：复用统一引擎的语音单轮服务及至少三轮连续演示。

验收：同轮异文和过期版本返回 409；取消/重试不串轮；语音端不能绕过事实及权限；测量 p50/p95。

### 阶段 14：多端、性能与部署

学习：客户端封装、中心服务、数据库并发、CI/CD 和运维。

- [ ] Windows 安装包、Android 客户端与同一 API/身份规则对接。
- [ ] 验证真实设备采集、复制、撤销、升级、断网与恢复。
- [ ] 压测后决定 PostgreSQL、索引、队列及多实例方案。
- [ ] Docker、HTTPS、就绪检查、请求追踪、模型/工具指标和错误告警。
- [ ] 建立密钥轮换、备份恢复、保留删除、发布与回滚流程。
- [ ] 验证文本和语音 p95 ≤ 8 秒目标；记录无法达成时的具体瓶颈。

产出：可部署、可恢复、可观测的团队试点版本。

验收：目标环境恢复演练成功；并发隔离和设备撤销有效；安装包真机流程通过；性能以实测为准。

### 阶段 15：试点后的持续工作

学习：如何用真实反馈改善产品，同时维持事实和风险边界。

- [ ] 按业务授权开展小范围试点，建立明确问题清单和版本基线。
- [ ] 分析知识未命中、错误工具路由、反复澄清、修改和放弃原因。
- [ ] 扩充试听、先修/硬件、适配评估、学习支持、就业统计等业务工具。
- [ ] 按证据决定是否引入混合检索、更多模型、流式输出或框架。
- [ ] 新工具、新知识和新 Skill 均经过评测与审核，记录灰度和回滚结果。

产出：有优先级的迭代计划、版本效果对比和可追溯的知识/工具更新。

验收：每次改动有具体问题、验证证据和回滚点；采纳率提升不能掩盖事实或风险退化。

## 5. 五个交付里程碑

| 里程碑 | 对应阶段 | 可以演示的成果 |
|---|---|---|
| M1：最小知识助手 | 0–4 | 创建会话、输入问题、查合成审核知识、输出有来源建议 |
| M2：销售 Agent 核心 | 5–8 | 多意图、授权工具、长对话记忆、最终护栏和建议失效 |
| M3：销售工作台 | 9–12 | 团队权限、人工协作、截图纠错、完整评测和审核发布 |
| M4：语音与多端 | 13–14 | 多轮语音、Windows/Android 和真实设备流程 |
| M5：试点与持续迭代 | 14–15 | 性能、恢复、灰度、真实效果和后续优化 |

## 6. 第一课的具体任务

第一课只完成阶段 0 和阶段 1 的最小部分：

1. 确定新工程的名称和目录，选择 Python 3.12 运行环境。
2. 定义首版三类业务与少量合成验收场景。
3. 初始化依赖、应用入口、配置示例与 Git。
4. 启动 FastAPI，访问健康接口和接口文档。
5. 解释请求如何进入路由并返回响应，记录启动/停止方法和下一课任务。

第一课结束应能独立启动服务并复述应用结构。下一课再实现会话和消息持久化。
